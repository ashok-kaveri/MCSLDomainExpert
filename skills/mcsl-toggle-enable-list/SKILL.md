# MCSL Toggle Enable List

Turns the account-scoped toggles from a release's cards into the exact text the dev team pastes to enable them for one or more merchant accounts.

## Inputs

- One or more account UUIDs (the merchant/store account, not a Trello or card id).
- A scope: a release name/guide already generated by `mcsl-handoff-docs` (preferred — reuse its index table), or a Trello list/lane to read directly if no guide exists yet.

## Steps

1. **Get the toggle list per card.**
   - If a combined support guide already exists for this release (`data/handoff_docs/...md`), read its `Included Story Cards` index table — the `Toggle Name` column already lists the exact per-card toggle key(s), comma-separated when a card has more than one.
   - Otherwise, pull the lane's cards via `mcsl-trello-operator` and run `build_handoff_context` / `detect_toggles` from `pipeline/handoff_docs.py` the same way the handoff-docs skill does, then take `ctx.toggle_names`.
   - Skip cards whose toggle is `None` / not detected.

2. **Classify each toggle key's identifier segment.**
   - Template form: starts with the literal placeholder `{accountUUID}` — the whole placeholder is the identifier segment.
   - Literal-example form: the card's own evidence hardcoded a real UUID instead of a placeholder (e.g. `21f0a963-e402-4c73-b8e5-ccb7ad11f5ac.woocommerce.bundle.classification.enabled` — that UUID is the reporter's own test account, not a fixed constant). Treat the leading UUID as the identifier segment; the suffix after it (`.woocommerce.bundle.classification.enabled`) generalizes to any account the same way the template form does. Confirm this generalization is safe by checking the card evidence names the flag as account-scoped, not hardcoded to that one account — if genuinely unsure, say so rather than guessing.
   - No-prefix form: a bare flag name with no UUID and no `{accountUUID}` placeholder anywhere in it. Do not invent a prefix. List it separately as "not account-keyed" and do not include it in the `"<uuid>.<flag>": true,` block.

3. **Validate every given account UUID before substituting.**
   - Must be exactly 5 dash-separated hex groups of length 8-4-4-4-12 (36 characters total, 4 dashes).
   - If a UUID is short, long, or malformed, do not silently pad, truncate, or guess the missing/extra characters. State exactly what's wrong (which group, how many characters off) and still show it substituted as given, clearly flagged, so the user can compare and correct it — never present a corrected guess as if it were the value they gave.

4. **Emit the result** as a fenced code block, one line per toggle, in this exact shape:
   ```
   "<accountUUID>.<flag>": true,
   ```
   Group by account UUID, in the order the UUIDs were given. If multiple UUIDs were requested, repeat the block per UUID with a heading naming which account it's for.

5. **List anything left out** — no-prefix toggles, or toggles you could not confidently generalize — with a one-line reason each.

## Guardrails

- Never invent a toggle not backed by actual card/comment evidence.
- Never silently repair a malformed UUID.
- This skill only produces text. There is no toggle-write API in this repo — enabling a toggle happens outside this pipeline (the developer applies it, per the existing Toggle Rules workflow in `CLAUDE.md`). Do not claim or imply anything was enabled.
- If the user also wants this sent to the dev team, that is a Slack send — treat it under the same approval rules as `mcsl-handoff-docs`' Slack Delivery section: dry-run/show the content and target, and only send after explicit approval unless the destination was already named in the same request.

## Final Response

Return the fenced code block(s) exactly as specified above, plus the exclusion list from step 5 if non-empty. Do not add explanatory prose inside the code block itself — the dev team pastes it as-is.
